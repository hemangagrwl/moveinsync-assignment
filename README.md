# Billable Distance Service

Rebuilds the billable kilometres of a cab trip from GPS that drops out, lies and arrives late,
and explains every kilometre so a vendor dispute can be answered line by line.

MoveInSync backend case study 1 (GPS gap backfill and billable distance reconstruction), advanced track.

| | Result |
|---|---|
| Accuracy vs. ground truth, 10,000 synthetic trips | engine median error **+0.40 %**, mean absolute **0.44 %** (naive sum: p5 **−29 %**, p95 **+277 %**) |
| Spec example: 31 km trip, 22 min GPS loss, 2 drops in the dark | naive sum **24.23 km**, engine **30.99 km**, 4 routed segments, **1** provider call |
| Throughput (engine, 14.5 M pings) | **2.7 ms** per 1,500-ping trip (p50), 13.8 ms p99, **313 k pings/s per core**, 50 MB per worker |
| Provider calls per trip | 2.76 if you call once per gap → **1.00** batched → **0.00** on recompute (pinned + cache) |
| Provider dies halfway through 2,000 trips | 1,000 trips go DEGRADED, all recomputed after recovery, **2,000 / 2,000 totals identical** to the healthy run |
| Determinism | Hypothesis property tests: shuffled, duplicated and late-delivered pings bill the **same metres and fingerprint** |
| Tests | 90 automated tests (unit, property, API, failure injection, threaded concurrency) |

Then, from a Python 3.11+ environment with the project installed (`pip install -e ".[dev]"`):

```bash
python scripts/demo.py
```

The demo ingests a messy trip (shuffled, duplicated, some pings held back), computes the
explained distance, closes the invoice, delivers the late pings, prints the signed
adjustment that appears in the ledger, and shows that another tenant gets a 404.

**Live failure demo:** `docker compose stop router`, compute a trip (it comes back
`DEGRADED`; Grafana shows the breaker go red), `docker compose start router`, and watch the
trip flip to `COMPLETE` by itself within a few seconds.

On Windows use `127.0.0.1`, not `localhost`: `localhost` tries IPv6 first and adds about
200 ms to every new connection.

## How a distance is built

```
raw pings ─► clean ─► anchors ─► place anchors ─► merge ─► classify segments ─► route real gaps ─► round ─► sum
             │         │           │                         │                    │
             │         │           │                         │                    └ one batch per trip:
             │         │           │                         │                      pinned → cache → provider
             │         │           │                         └ SHORT_GAP_AERIAL → PARKED → (routed)
             │         │           └ redundant if GPS passes it; fallback anchors retimed into their gap
             │         └ actual → profile home (ad hoc) / planned (planned); no-show behind a flag; office ≤ 400 m
             └ invalid → out of window → accuracy > 50 m → dedupe → teleport > 120 km/h → jitter < 8 m
```

Every segment ends up with exactly one rule. The rules are evaluated in a fixed, versioned order.

| Rule | When | Distance |
|---|---|---|
| `SHORT_GAP_AERIAL` | consecutive points < 70 s apart at ≤ 120 km/h | haversine |
| `PARKED` | ≥ 70 s apart, implied speed < 5 km/h | haversine |
| `ROUTED` | any other gap; provider answer accepted | driving distance |
| `REJECTED_MAX_DISTANCE` | routed distance > 100 km | 0, trip flagged for review |
| `REJECTED_SPEED` | routed speed **and** aerial × 1.4 speed both > 120 km/h | 0, trip flagged for review |
| `DEGRADED_AERIAL` | provider failed or circuit open | haversine × 1.4, trip `DEGRADED` |

Each result carries line items (consecutive `SHORT_GAP_AERIAL` hops are merged into one item;
every other rule is one item per segment), anchor decisions (`USED` / `RETIMED` / `REDUNDANT`
with original and final time), rejected-ping counts by reason, provider statistics, the rule
version and an input fingerprint.

### Determinism, units and rounding

* Coordinates are quantised to 1e-7° (about 1 cm) on the way in and stored as integers, so an
  in-memory run and a database round trip are bit-identical.
* Each segment is rounded to whole metres **once** (half-up); totals are exact integer sums.
  Metres become invoice kilometres in one function: 2 decimals, half-up (`30 605 m → 30.61 km`).
* Every tie is broken explicitly: duplicates by accuracy, then coordinates; merge order by
  time, then anchor before ping, then coordinates.
* The rule version is `name#sha256(all thresholds)`. Changing any threshold changes the
  version and the fingerprint, so two results from different rules can never be confused.
* Floating-point functions (`sin`, `cos`) are only bit-identical on the same platform and
  library build. That is why the Docker image is the unit of determinism, and why route
  answers are pinned per trip.

### Rule tuning that was measured, not guessed

The two thresholds not given by the spec were chosen against ground truth (500 trips):

| Stationary-jitter filter | Mean abs. error | p95 | Worst trip |
|---|---|---|---|
| off | 1.28 % | +2.44 % | 6.3 % |
| 5 m | 0.63 % | +1.15 % | 3.3 % |
| **8 m (chosen)** | **0.43 %** | **+0.81 %** | **3.1 %** |
| 12 m | 0.27 % | +0.60 % | 2.3 % |

8 m was kept rather than 12 m, so the threshold isn't overfitted to the synthetic noise model.
Cache cell size was swept the same way (1,000 trips): 55 m / 111 m / 222 m / 444 m cells give
cross-trip hit rates of 0.1 / 0.2 / 0.4 / 2.1 % and mean absolute error 0.47 / 0.47 / 0.48 / 0.58 %. Coarse cells cost
accuracy and buy almost nothing on random gaps, so cells stay at ~55 m.

## Engineering choices

### Caching (what can go stale, and for how long)

| Cache | Key | Value | Staleness bound |
|---|---|---|---|
| Route cache (in-process LRU, 200k entries) | directed cell pair (~55 m cells) | centre-to-centre driving metres | TTL 24 h; only road-network changes make it stale |
| Pinned route evidence (stored per computation) | cell pair | metres used on the last COMPLETE result | intentionally never refreshed: an invoice must be reproducible |

The provider is only ever asked about cell centres. The answer is then scaled to the real
endpoints by the ratio of their straight-line distances. So a cached answer never depends on
which trip asked first, and sharing the cache can't change anybody's bill. Failures are never
cached. On synthetic data the cross-trip hit rate is low (random gaps rarely share both
endpoint cells). The measured win comes from batching (2.76 → 1.00 calls per trip) and from
recomputation (1.00 → 0.00). In production `backfill_route_lookups_total{source}` shows the
real hit rate.

### Failure handling

See the failure-mode table in [docs/DESIGN.md](docs/DESIGN.md). In short: circuit breaker
(5 failures → open, 10 s → one trial), `DEGRADED` instead of errors, automatic recompute
when the breaker closes, one-retry budget for blips, leases for crashed workers, idempotent
writes, an append-only ledger and a watermark that ignores stale results.

### Security and privacy

* JWT (HS256) with tenant and role claims; the tenant id comes **only** from the token, and
  every repository query that starts from client input filters by it. Cross-tenant access is a
  404 (existence is not leaked). Tested on every trip endpoint.
* Roles: `ADMIN` (everything in the tenant, closing invoices), `OPERATOR` (ingest, compute,
  inspect), `EMPLOYEE` (only trips they rode in, totals only, no coordinates or other riders).
* Unknown user and wrong password take the same time and return the same error.
* No personal data in logs: a structlog processor redacts location/contact keys, and a test
  captures every log event of a full flow and asserts no coordinate value appears. Validation
  errors report the field and the problem, never the submitted value.
* Error responses carry a stable `code`, a client-safe `message` and the `request_id`.

one writer at a time, and uvicorn workers on Windows do not share connections well. Those runs
reached about 150 read requests/s, and write latency there is not representative. The numbers
that matter come from the Linux/Postgres stack:


### Complexity and where it stops scaling

| Step | Time | Space |
|---|---|---|
| Cleaning (sort, dedupe, vectorised speeds) | O(n log n) | O(n) |
| Teleport / jitter passes | O(n), with a vectorised fast path | O(n) |
| Anchor placement | O(a · w) for a anchors, w pings in the ±10 min window | O(n) |
| Segment classification | O(n) vectorised | O(n) |
| Routing | O(g) unique cell pairs, ⌈g / 50⌉ provider calls | O(g) |

Per trip it is effectively linear. A 1,500-ping trip needs ~100 KB of arrays, and trips are
independent, so the engine scales out by process or by machine. Where it stops scaling:

1. **Routing provider quota.** One call per trip on a cold cache; at a 200 calls/s quota that
   caps first-time computes near 200 trips/s, whatever the CPU count. Mitigations: a shared
   (Redis) cache, larger batches, routing only for invoices that are about to close.
2. **Database writes.** Each computation stores its explained result (~10 to 50 KB) and track
   (~100 KB). At fleet scale (~1M trips/day) that is around 100 GB/day of history. It would need
   partitioning by month, a cold-storage policy for tracks, or storing tracks in object storage.
3. **One hot trip.** Recomputes of one trip serialise on its row lock. That is intentional (it
   protects the ledger) and harmless, because late-ping recomputes are debounced.
4. **SQLite** is only for local development and tests: it has one writer at a time.

## Trade-offs and what was left out

* **Estimates are served, never invoiced.** `DEGRADED` results are visible immediately
  (availability), but closing an invoice requires a `COMPLETE` result on the latest evidence
  (consistency for money).
* **Rejected segments bill 0 m and flag the trip for review**, instead of guessing. A wrong
  guess in either direction is a dispute; a review flag is a workflow.
* **Spec-literal speed check.** A routed distance that implies > 120 km/h is still accepted
  when aerial × 1.4 is plausible (the spec only rejects when both are too fast). Documented as
  a candidate rule change for v2.
* **Synthetic city.** Ground truth needs a road network where the true route is known. The
  generator drives cabs on a Manhattan grid and the mock provider returns grid (L1) distances.
  Real-road accuracy needs a labelled sample of real trips. OSRM could replace the mock behind
  the same `RoutingProvider` interface.
* **Left out on purpose:** Kalman or map-matching smoothing (bigger accuracy gains on curvy
  roads, but harder to explain to a vendor than "straight line between two fixes 4 s apart"),
  a message broker (the outbox-style job table is enough at this scale and keeps the run to one
  command), Alembic migrations (the schema is created on start), Redis (the cache interface
  allows it, and the in-process cache is honest about its hit rate), refresh tokens, and rate
  limiting at the edge.

## Assumptions

* One direction per trip: `LOGIN` (pickups then office) or `LOGOUT` (office then drops); the
  office anchor sits at the office end of the trip.
* A reported pickup/drop is valid if the coordinates are real, its time is within the trip
  window ± 15 min, and it is within 2 km of the planned point (or profile home for ad-hoc riders).
* A missing accuracy value means "not reported", not "bad".
* Pings outside the trip window are not billable.
* Invoice kilometres have 2 decimals.

## Why Python

Java is preferred by the brief; Python was a deliberate choice:

* The hot path is numerical work on arrays of pings. Cleaning, haversine, speeds and rule
  classification are vectorised numpy, giving 313k pings/s per core, and trips run in parallel
  processes (no GIL contention).
* The OOP criteria are met with the same tools Java would use: an abstract `LocalRule` with
  polymorphic rules, a `RoutingProvider` protocol with three implementations, a decorator-style
  `ResilientRouter`, immutable value objects, and controller → service → repository layering.
* Type safety: strict mypy configuration, Pydantic models at the edge, and frozen dataclasses
  in the core.
* Property-based testing (Hypothesis) proves the determinism claim mechanically.
